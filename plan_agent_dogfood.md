# Plan: dogfooding — use the library as a newcomer agent would, on real engineering problems

Branch `feature/agent-dogfood`, based on `integration/next-level`.

## Why

Five branches have just changed how pipelines are written and checked (strict parser, snapshot / sweep / describe, controls from annotations, figures, heatmap colorbars, `interactive_pipe.draw`, the `interactive-pipe` command, a rewritten skill). Nobody has yet used all of it together to do real work. The goal of this branch is to find out whether an agent that knows only the skill can write concise, correct scientific visual-debugging tools — and to turn everything that goes wrong into a precise list.

## Method — this matters more than the output

1. Read ONLY `src/interactive_pipe/agent/build-interactive-pipeline/SKILL.md` first. Do not read the library source or the docs before writing an example. When the skill is not enough and you have to look something up, that is a finding: write down what was missing, where you found it.
2. For each example below: write it, run `describe`, take a snapshot, **read the PNG**, sweep one parameter, read it, fix. Keep a friction log as you go (in Status): every error message that did not tell you what to do, every surprise, every place where you wrote boilerplate that the library should have absorbed, every time the snapshot differed from what you expected, with the minimal reproducer.
3. Count for each example: lines of pipeline code (filters + pipeline, excluding data generation), number of iterations before the snapshot was right, number of look-ups outside the skill.

## Examples to write — `demo/gallery/`, one file each, synthetic data only (numpy; scipy only if already installed; no downloads, no new dependency)

Pick problems an engineer would really debug visually; each file under ~80 lines, runnable as a script with `gui="auto"`, each with a docstring saying what to look at:
1. **Camera ISP**: Bayer mosaic → demosaic → white balance → gamma, with an error map (colorbar, diverging) against the ground truth and a PSNR readout.
2. **Frequency-domain filtering**: image, its log-spectrum as a heatmap, a band-pass mask controlled by two radii, the filtered image; a matplotlib figure with the radial power profile.
3. **1D signal processing**: noisy chirp, FIR/IIR filter with cutoff and order controls; curves for the signals, a figure with the frequency response (magnitude and phase on twin axes).
4. **Detection overlay**: blobs on a noisy background, threshold + minimal area; boxes and labels with `draw`, a table of detections, precision / recall as text.
5. **Optimisation trace**: gradient descent variants on a 2D function; contour figure with the trajectory, loss curve; controls for learning rate, momentum, steps (`Literal` for the optimiser).
6. **Geometry / calibration**: a checkerboard warped by a homography plus lens distortion; controls for the distortion coefficients; residual vectors or an error heatmap.
7. **Control engineering**: step response of a second-order system with PID gains; curves for response and command, a figure with the Bode plot.
8. One of your choice where you expect the library to be a poor fit — to find the edges.

Use annotation controls in some examples and decorator controls in others; use sweeps to choose the default values and keep the sweep image of two or three examples for the docs.

## Deliverables

- `demo/gallery/*.py` + `test/test_gallery.py` (each runs headless, snapshot not blank — reuse the helpers of `test/test_demos_headless.py`).
- `docs/gallery.md` (in `mkdocs.yml` nav): one snapshot per example (PNG under `docs/images/gallery/`, generated by a small script `scripts/make_gallery.py` so they can be regenerated; keep each PNG under ~150 kB), the code, one sentence on what the tool is for.
- **The friction log**, in Status, ordered by how much time each item cost, each with a reproducer and a proposed fix. This is the main deliverable.
- Skill improvements that follow from the log: edit the packaged skill (source of truth) and re-install the copy (`python -m interactive_pipe skill --install --project . --force`); keep it under the line limit of `test/test_skill_code_blocks.py`; its code blocks are executed by that test. Add what you had to look up; remove what you never needed.
- A second pass at the end: re-read your eight examples and make them as short as the library allows; report the line counts before / after.
